# تنظيم المودولات وملكية عمل الوكلاء

تعليمات مكملة لدليل `GEMINI_EXECUTION_PLAYBOOK_AR.md` وقائمة العمل، بناء على توجيه المالك في 2026-11-03. تحكم كل دفعة في المشروع، مع الالتزام بقرار `../architecture/ADR-0001-MODULAR-MONOLITH.md` وخريطة `../architecture/PROJECT_MAP.md` وAGENTS الحالية.

## النتيجة المطلوبة

واجهة الأصل وسلوكه فوق مشروع منظم يسهل تطويره، بملكية واضحة لكل حقيقة وخدمة ومكون. لا يُقبل إصلاح صفحة بحشر أعمال الطالب والمحتوى والتقييم والصلاحيات في service أو component واحد. ولا يُنشأ مودول جديد لاسم شاشة فقط مع تكرار منطق مودول موجود.

## استلام ما يعمل عليه الوكلاء الآن

هذه التعليمات تسري على الدفعات التالية؛ لا تطلب إلغاء عمل الوكلاء الحاليين أو استبدال ملفاتهم قبل استلامها. بعد انتهاء مهامهم اجمع لكل وكيل: الهدف، الملفات، base/head SHAs، التغييرات، نتائج الفحوص، التبعيات، والمتبقي. افحص git status وdiff ومشكلات التداخل، وأعد فحص النسخة المجمعة. لا تخلط نجاح اختبارات فروع منفصلة بنجاح ناتج الدمج.

راجع المنفذ الموجود قبل أي إعادة تنظيم: إعادة التنظيم نفسها تغيير قابل للكسر، فتكون محدودة وذات سبب وأدلة، مع الحفاظ على الملفات الصحيحة والعمل القائم.

## تحديد المودول الصحيح قبل كتابة الكود

لكل قدرة اكتب module-map.md داخل مجلد الدفعة يحدد:

1. الحقيقة أو القرار الذي تنتمي إليه القدرة، والمودول المالك الحالي وأدلته من الكود.
2. المدخلات والمخرجات والجداول التي يملكها، والمودولات التي تستهلكه.
3. الواجهات أو الأحداث التي تتصل بها المودولات، والتبعيات واتجاهها.
4. هل المطلوب استعمال قدرة موجودة، توسيعًا محدودًا فيها، أم مودولًا جديدًا؟ ولماذا؟
5. الملفات المخطط إنشاؤها أو تعديلها وخطة اختبار المستهلكين.

أمثلة ملكية تستدل بها ثم تحققها من التنفيذ: taxonomy للتصنيف؛ content للموضوع والدرس وروابطهما؛ questionbank للسؤال وإصداره؛ assessment لتعريف الاختبار والمحاولة والتصحيح؛ learning للتقدم وأدلة التعلم؛ commerce للاستحقاق؛ organizations للعضوية والتكليفات المدرسية؛ identity للهوية. الواجهة تجمع النتائج عبر عقود واضحة ولا تستولي على القرارات الخلفية.

إذا كانت مسؤولية نطاق مستقلة غير موجودة حقًا فأنشئ مودولًا مناسبًا بعقد محدد. إذا كان الموجود يدعمها جزئيًا فوسعه دون بناء نسخة موازية. إذا كان ملف كبير يجمع مسؤوليات مختلفة فافصل القدرة المطلوبة مع اختبار عدم تغيير السلوك؛ لا تعمل إعادة كتابة شاملة أثناء إصلاح صغير.

## تنظيم Go

اتبع نمط المشروع القائم، مثل `internal/<module>/domain` و`application` و`repository/postgres` و`transport/http` حيث يستعمله المودول. لا تنشئ طبقات فارغة لإكمال شكل نظري.

المعمار المعتمد Modular Monolith: نطاقات صريحة داخل تطبيق Go، وworker للمهام؛ لا تحولها إلى microservices لمجرد التنظيم. `internal/platform` للبنية المشتركة فقط. حدّث عقد HTTP في `api/openapi` عند تغيير API وفق تنظيم المشروع، واجعل migrations تغييرات إصدار صريحة؛ لا تعديل schema ارتجالي أثناء التشغيل.

- domain: المعاني والحالات والقواعد الخالصة، دون HTTP أو SQL أو اعتماد على الواجهة.
- application: حالات الاستخدام وتنسيق القرارات عبر interfaces محددة والتحقق من الصلاحيات وفق المعمار القائم.
- repository: الاستعلامات والمعاملات وتطبيق قيود التخزين؛ لا يعيد اختراع قواعد امتلاك النطاق أو الاستحقاق في كل مستهلك.
- transport: فك الطلب والتحقق الحدودي وتقديم الاستجابة وتعيين الأخطاء؛ لا يُحشر فيه منطق التعلم أو التصحيح.
- composition root في cmd/api أو cmd/worker: توصيل الخدمات والمستهلكين فقط، لا يتحول إلى موقع قواعد العمل.

لا تستورد repository لمودول آخر لتقرأ جداول ملكه من كل مكان. استخدم واجهة قراءة/خدمة/حدث وفق الموجود. إن كان استعلام تقريري مشترك مسموحًا بالمعمار فوثق ملكيته ودلالته واختباره بدل ادعاء أن منع joins قاعدة عامة. حافظ على اتجاه التبعيات وتجنب import cycles؛ لا تستخدم shared/common للهروب من حدود المسؤولية.

تعريف الاختبار وربطه بالمحتوى، واستحقاقه، والتصحيح، وأثره على الإتقان قدرات مترابطة لها أصحاب مختلفون. لا تنقلها كلها إلى مودول الطالب لأن الشاشة تجمعها. المواءمة تكون بعقود مستقرة، وحالات الفشل وإعادة المحاولة موثقة.

## تنظيم الواجهة دون تغيير الأصل

اتبع feature folders القائمة، مع client/types/adapters/components/hooks/pages حسب الحاجة الفعلية. page تنسق الشاشة، والمكونات تعرض وحدات مفهومة، وclient يملك اتصال API. لا تجعل JSX واحدًا يحتوي كل الأنواع والمشغل والاختبار ولوحة الإدارة والخدمات.

انقل طبقة العرض الأصلية أو كيّفها كما تقرر سياسة المطابقة. افصل حجم التنفيذ الداخلي مع بقاء ترتيب العناصر وCSS والتفاعلات الأصلية. المكوّن المشترك يشارك سلوكًا موحدًا بالفعل؛ لا توحد شاشتين مختلفتين ظاهريًا على حساب الأصل. لا تستعمل global CSS لإصلاح شاشة واحدة؛ احفظ styles في نطاقها أو في token أصلي مشترك.

لا تضع أسرارًا أو قرارات RBAC أو التصحيح أو الاستحقاق في الواجهة. لا تجعل تغيير نوع DTO يكسر بقية مستهلكيه بصمت؛ احصرهم بالبحث واختبرهم، ووفر adapter عند اختلاف نموذج العرض.

## فريق متخصص وملكية كتابة

| التخصص | المسؤولية | حدود العمل |
|---|---|---|
| المشرف Codex | اعتماد النطاق والعقود والأدلة ومراجعة التكامل | يعيد عيوبًا محددة؛ لا يعدل الملف الذي يملكه منفذ نشط بالتوازي |
| قائد التنفيذ Gemini | تنسيق الدفعة والملكية والدمج وإصلاحات التكامل | مسؤول عن نتيجة الشغل المجمعة، لا يكتفي بجمع تقارير الوكلاء |
| باحث الأصل | الواجهة والفلسفة والرحلات والمراجع | قراءة وأدلة؛ لا يكتب بديلًا قبل فهم المرجع |
| مختص الواجهة | المكونات والـadapters وRTL والمطابقة | ملفات واجهة محجوزة ومستهلكون معلومون |
| مختص Go والنطاق | حالات الاستخدام والعقود والحماية | ملفات المودول المعين فقط |
| مختص التخزين | القيود والمهاجرات والاستعلامات والتكامل | بيانات معزولة؛ لا إنتاج ولا تعديلات محتوى |
| مختص التحقق | الاختبارات والمتصفح والصور والانحدار | لا يضعف الاختبارات لجعل التنفيذ ينجح |

هذه تخصصات وليست إلزامًا بتشغيل ستة وكلاء في كل مرة. اجمعها حسب حجم الدفعة وموارد الجهاز. ابدأ بقارئين مستقلين وكاتب محدد وفاحص عندما يكفي ذلك. لكل وكيل تكليف مكتوب: ID، الهدف، ملفات القراءة، owned_files، ملفات ممنوعة، base SHA، العقد، الأدلة المطلوبة، التبعيات ونقطة التسليم.

## سجل حجز الملفات

داخل كل دفعة `ownership.md` يحتوي جدولًا: الملف/المجلد، المالك، المهمة، يبدأ من SHA، حالة العمل، المستهلكون، موعد التسليم المنطقي. حالات الحجز: محجوز/جارٍ/سُلّم/راجع/دُمج. لا تعتمد وعد وكيل بأن ملفات غيره لن تتأثر؛ راجع diff الفعلي.

الملفات المشتركة مثل router وcmd/api وtypes المشتركة وpackage/lock والمهاجرات يكتبها شخص واحد في الدفعة، عادة قائد التكامل. الوكيل يرسل التغيير المطلوب لقائد التكامل بدل إجراء تعديل منافس. أرقام migrations تحجز مركزيًا بعد فحص أحدث رقم؛ لا تنشئ مهاجرتين بالرقم نفسه. عند استخدام worktrees، سلم commit محددًا ثم ادمج بالتتابع مع حل التعارضات ومراجعة المعنى لا العلامات فقط.

## منع الإصلاح الذي يكسر منطقة أخرى

قبل التعديل ابحث عن جميع مستهلكي الرمز والعقد والجدول والإعداد، وسجل impact-map.md: المستهلك، السلوك المعرض للتأثر، فحصه. غطِّ على الأقل مسار النجاح والرفض والخطأ الذي يتأثر بالتغيير.

افحص التوافق مع البيانات القديمة، والإصدارات، والحقول الاختيارية، والقيم false/null، وترتيب الاختيارات، والتصفح. لا تُسقط عمودًا أو تغير تصحيحًا أو اشتراكًا أو صلاحية ضمن تنظيف الملفات. أي تغيير لذلك له عقد مستقل ودليل وقرار وفق قواعد المشروع.

التكامل بالتتابع: تثبيت العقد → تنفيذ مالك البيانات/الخدمة → توصيل العميل/العرض → اختبار HTTP والتخزين → متصفح → صور مقارنة → مراجعة جميع المستهلكين المتأثرين → CI على SHA المجمّع. لا يصبح مجلد كامل «سليمًا» بسبب نجاح اختبار خدمة واحدة.

إذا كُسر فحص قائم: أعد إنتاجه، حدد هل التنفيذ غيّر العقد أم fixture قديم، أصلح السبب مع إبقاء حماية السلوك. سجل الفشل وإعادة الفحص. لا تحذف اختبارًا أو تتجاهل خطأ لأن وكيلًا آخر مسؤول عنه.

## تسليم التنظيم

أرفق مع كل دفعة module-map وownership وimpact-map، وقائمة ملفات جديدة وسبب وجود كل منها. حدث خريطة المشروع عند إضافة مودول حقيقي وعقد معماري موجز عند تغيير حدود المسؤولية. سجل ما بقي معقدًا أو كبيرًا دون ادعاء إعادة تنظيم المشروع كله. الشكل النهائي المطلوب: وظيفة لها مالك واضح، ملفات مفهومة، وعقود واختبارات تحفظ بقية المنصة.

## النص الذي يبدأ به التكليف القادم

Gemini: بعد انتهاء وكلائك الحاليين اجمع تسليماتهم وافحص النسخة المجمعة أولًا. اقرأ دليل التنفيذ وقائمة النطاق الشامل وهذا العقد. احجز الملفات ووزع التخصصات قبل العمل. استخدم مودولات المشروع القائمة، وأنشئ مودولًا جديدًا فقط لمسؤولية مستقلة غير موجودة، ولا تجمع المسؤوليات في مودول واحد أو تنسخ منطقًا قائمًا. سلم خريطة الملكية والتبعيات والأثر مع كل دفعة. احتفظ بواجهة الأصل وسلوكه، واختبر المستهلكين المتأثرين وصور المقارنة قبل طلب اعتماد Codex.
