## 1. الحكم التنفيذي

1. **لا إعادة بناء شاملة من الصفر.** الموجود في Go ليس مجرد صفحات تجريبية؛ هناك وحدات هوية وتصنيف وأسئلة ومحتوى واختبارات ومدارس وتقارير ومراحل اختبارات مدمجة. إعادة بنائها بلا دليل فشل معماري مضيعة ومخاطرة.
2. **لا اعتماد تلقائي للشكل أو سير العمل بسبب الدمج.** نتيجة TESTED أو MERGED تثبت نطاق الاختبارات المنفذة فقط. جميع الواجهات الأصلية والأزرار والعلاقات تحتاج عقد تكافؤ ظاهر للمستخدم وإثباتًا فعليًا.
3. **نموذج البناء: Modular Monolith + Vertical Capability Slices + Exact Legacy Presentation.** دومين واحد يملك الحقيقة والقرارات، واجهات مختلفة بحسب الدور كما صُممت في الأصل، ورحلة مكتملة تربط الجميع.
4. **لا كتابة متزامنة متعارضة.** حساب Work هو كاتب التنفيذ الجاري؛ المراجع المستقل يفحص المصدر وGitHub والاختبارات ويرفع ملاحظات محددة. لا دمج شامل لشغل Gemini أو فروع قديمة، ولا تغيير لبيانات الإنتاج.
5. **القرار المؤجل الوحيد هو ما يغير سلوكًا معتمدًا أو يعرض بيانات للخطر.** تفاصيل Go الداخلية من مسؤولية المهندس. لا يُستدعى المالك للبت في كل ملف أو حزمة.

## 4. الهيكل الهندسي الصحيح

### 4.1 وحدات Go: ملكية منطق الأعمال لا ملكية الشاشات

أُحصيت الدلائل الموجودة فعليًا في internal: ai, assessment, commerce, communication, content, identity, learning, media, operations, organizations, parents, platform, questionbank, realtime, reporting, taxonomy.

المعمار المقصود كما في عقد Go الحالي:

- **React/Vite/TypeScript:** العرض الأصلي ومكونات الشاشة وحالاتها، دون اتخاذ قرار درجة أو أهلية أو صلاحية نهائية.
- **Typed API clients/presentation adapters:** ترجمة بيانات Go إلى احتياجات المكونات الأصلية، واستيعاب اختلاف التسمية/المعرفات دون إعادة Zustand/Node/Mongo القديم بصورة عمياء.
- **Go domain/application:** قواعد الأعمال وفحص الأوامر والسياق والصلاحيات، ومالك واحد لكل حقيقة؛ الواجهات المتعددة تستدعي الخدمة نفسها.
- **Go transport/http:** مدخلات موثقة ومحددة الحجم، جلسة/CSRF، استجابات أخطاء ثابتة.
- **PostgreSQL repository + migrations:** مفاتيح وعلاقات وفهارس وسجلات وحركات ذرية ونسخ؛ لا كتابة جداول دومين آخر عشوائيًا.
- **Redis/R2/AI/realtime:** خدمات مساعدة بحدود واضحة؛ الصور والفيديو خارج تدفقات JSON الثقيلة قدر الإمكان، والذكاء الاصطناعي ليس سلطة تصحيح.

**قاعدة الملكية:** تصنيف المسار والمهارة لدى taxonomy؛ الموضوع/الدرس لدى content؛ السؤال والإصدار لدى questionbank؛ تعريف الاختبار والمحاولة والنتيجة لدى assessment؛ تقدم/إتقان المهارة لدى learning؛ التقارير لدى reporting؛ المدرسة والتكليف لدى organizations؛ الاستحقاق لدى commerce. لا توجد نسختان سلطويتان من نفس الكيان.

إذا احتاج موديول بيانات موديول آخر، يستخدم عقدًا صريحًا في application/port أو استعلام projection مضبوطًا بوثيقة ملكية، ولا ينسخ الجداول/المنطق لمجرد تقليل imports. لا تُنشأ Microservices؛ تبقى بنية Modular Monolith ما لم تثبت حاجة تشغيلية مغايرة لاحقًا.

### 4.2 الوحدة المناسبة للتسليم: رحلة رأسية، لا صفحة وحدها ولا Backend وحده

نرفض طريقتين منفردتين:

- **لوحة لوحة فقط:** قد تنتهي صفحات جميلة لكن بمضاعفة الاختبارات والقرارات وانقطاع الروابط بينها.
- **موديول Backend فقط:** قد ينجح API بينما مدير المنصة لا يجد بطاقة المسار أو الطالب لا يفتح درسًا.

الأسلوب المعتمد: **موديول يملك الحقيقة + جميع الواجهات التي تستهلكه + رحلة استخدام مكتملة + اختبارات رفض ومظهر وحفظ**. تنفَّذ على دفعات صغيرة يمكن مراجعتها ودمجها مستقلًا.

## 6. منهج التقييم والتسليم لكل شاشة وزر

سجل موحد بصف لكل حالة واختبار:

**screen_id | role | URL | legacy_SHA/file | Go_SHA/file | viewport | state | action/control | expected legacy behavior | actual Go behavior | HTTP/DTO | Go module/service | PostgreSQL table/relation | auth/entitlement | evidence/tests | verdict | priority | owner | next step**.

الحالات الإلزامية: loading، loaded real data، empty، error، forbidden، locked/free، modal open/close، search/filter، saved/persisted، back/reload/deep-link، mobile/keyboard/RTL، server failure and retry.

الحكم الدقيق: UNKNOWN → MAPPED → GAP_PROVEN → IMPLEMENTED → TESTED → VISUAL_VERIFIED → ROLE_DATA_PARITY_VERIFIED → PARITY_PROVEN. لا أرقام 100% من عدد الملفات أو route count أو اختبار مموّه.

**الاختبار البصري:** أصل وGo بنفس الحساب/الصلاحية/البيانات/الخط/viewport/DPR/المتصفح، مع صور paired للحالات المهمة ومراجعة الفرق. عينة أساسية 390 و820 و1440، وإضافة 360/430/768/1024/1366/1920 عند نقاط الانكسار والسبورة. ضبط البيانات الزمنية لتثبيت المقارنة؛ لا لقطات حساسة من الإنتاج.

**اختبار السلوك:** من زر المستخدم إلى HTTP إلى Go إلى PostgreSQL ثم العودة للواجهة بعد Reload. اختبارات نجاح ورفض وسياق متغير، لا mocks وحدها. Unit/contract مفيدة لكنها لا تثبت التكامل.

## 7. أول شريحة حرجة: إدارة المسارات حتى ظهورها للطالب

**P0-A — واجهة المدير:** فتح لوحة الإدارة الأصلية → بطاقة إدارة المسارات → كل بطاقات المسارات → إنشاء مسار/تعديل الاسم والأيقونة واللون/الظهور → فتح بطاقة المسار → tabs: المراحل والمواد والمحاكيات والباقات والإعدادات → فتح بطاقة المادة → tabs: الدورات والتأسيس والتدريب والأسئلة والاختبارات والمكتبة وعرض الطالب.

**P0-B — عقد البيانات:** افحص الصلاحية والـDTO والحقول المحفوظة للعرض (path/subject settings) في Go؛ أضف فقط الفروق المفقودة في domain/API/migration بصورة توافقية، ولا تختلق JSONB يحجب علاقات كان يجب أن تكون مقيّدة.

**P0-C — المحتوى:** المهارة/Topic الصريح في نطاق path/subject، سؤال بنك مع نسخة وصورة، درس وفيديو ودورة، اختبار وتدريب، باقة/منحة، نشر/إخفاء/اعتماد. كل رابط له مالك ومعرف ثابت.

**P0-D — واجهة الطالب:** نفس بطاقات المسار والمراحل/المواد والتأسيس، روابط الفيديو/التدريب/الدعم دون تشغيل تلقائي، حالة المجاني/المقفل، عودة المستخدم وتقدم التعلم.

**P0-E — إثبات الرحلة:** admin create/edit → database persisted → student real GET → correct visibility/denials → course/lesson/training/attempt/result/report → return/reload → no cross-path contamination. اختبارات API errors تحفظ مسودة الإدخال ولا تختلق نجاحًا.

**المطلوب تقسيمه إلى PRs:** (1) عقد/حفظ إعدادات العرض ومطابقتها؛ (2) مساحة المسار/المادة عبر adapters؛ (3) أثر الطالب وقواعد الإتاحة/الأفعال؛ (4) اختبارات الرحلة واللقطات إن كانت مستقلة فعلًا. لا تغلق واجهة المدير قبل إثبات الطالب. إذا امتدت شريحة كبيرة، استخدم feature flags أو اجعل التغييرات غير المنشورة آمنة؛ لا تعرض حالة نصف منفذة للمستخدم.

## 8. مثال المدارس بالطريقة الصحيحة

عند الوصول لموديول المدرسة، لا ننسخ لوحة المدير وحدها:

1. مدير المنصة ينشئ مدرسة وعقدًا وصلاحيات، مع audit.
2. مدير المدرسة المفوض يرى الأقسام الأصلية ويضيف/ينقل طالبًا ويكوّن فصلًا ويكلف معلمًا بمادة.
3. المعلم يرى مادة وفصل تكليفه فقط، ويؤلف أو يختار أسئلة ويعد اختبارًا/حصة وفق السلطة.
4. الطالب يرى الاختبار/الحصة ضمن عضويته واستحقاقه، ويجيب؛ الخادم يحجب مفاتيح الإجابة ويصحح.
5. التقارير تفصل نتائج منصة/مدرسة/حصة، ويصل إليها المدير/المعلم/المشرف/ولي الأمر بحسب الصلاحيات.
6. اختبر إبطال التكليف أثناء الجلسة، تغيير المدرسة/الفصل، تحديث نتائج متأخر، مستخدم من مدرسة أخرى، محاولة مكررة، واستخدام URL أو ID غير مصرح.

**منع الخلط:** school membership ≠ teacher assignment ≠ assessment audience ≠ entitlement. وجود رابط أو إظهار زر لا يمنح الحق؛ السلطة في Go لكل طلب وكائن.

## 9. ضوابط PostgreSQL وGo

1. مفاتيح مستقرة، FK وUNIQUE وCHECK بحسب المعنى، مؤشرات بحث مقاسة، ومعاملة ذرية حين تعدل العملية عدة صفوف أو تنشئ Audit.
2. لا تعتمد على واجهة React في تفويض المستخدم أو تصحيح الإجابة أو تقرير الإتقان.
3. لا duplicate للأسئلة أو صورها داخل كل اختبار؛ استخدم المرجع/الإصدار والمعلومات التاريخية اللازمة للحفاظ على حقيقة المحاولة.
4. أي migration على بيانات فعلية: inventory، backup/restore، additive schema، اختبار rollback، staging backfill، reconciliation counts/IDs/hashes/grants، ثم موافقة مستقلة على cutover. لا هدم أو rewrite لنتائج الإنتاج.
5. وفّر idempotency لمحاولة/دفع/منحة/نقل متكرر، واختبر concurrency والطلب المتأخر وانسحاب التفويض. اختبارات go test -race للوحدات المتزامنة المستهدفة، لا الاكتفاء بغياب panic.
6. تمييز إلغاء الصلاحية وحق الاشتراك وتجددها عند الطلب؛ لا تحتفظ واجهة بسلطة قديمة بعد تغيير السياق.
7. استخدم OpenAPI الحالي لتثبيت عقد النقل وأخطاء الاستجابات؛ لا تخلق مسارًا ثانيًا سلطويًا لنفس العملية لتسهيل التوافق مع URL قديم.
8. لاحظ تعارضًا يحتاج تحققًا لا حلًا تخمينيًا: تاريخ Legacy يسجل سياسة تصحيح سؤال بنك أثناء محاولة نشطة، بينما بعض عقود Go تؤكد تثبيت نسخة الاختبار. يجب مقارنة أحدث Legacy وكود المحاولة/التصحيح في الحالتين، وتوثيق حقيقة السلوك قبل أي قرار؛ **لا تمس النتائج التاريخية المكتملة**.

### 9.1 الثوابت التربوية التي لا يجوز أن تضيع في تغيير المعمار

- **رحلة الإتقان:** مسار/مادة → موضوع/مهارة → تأسيس → تدريب → اختبار → نتيجة وتحليل دليل → مراجعة وعلاج → إعادة قياس. وجود صفحة نتيجة وحدها لا يكفي.
- **النطاق التعليمي:** كل Evidence/SkillProgress يجب أن يميّز الطالب والمسار والمادة والمهارة؛ لا يخلط نتائج القدرات والتحصيلي ونافس أو مواد المدرسة.
- **تصنيف الكمي المعتمد V1:** 25 مهارة رئيسية و95 فرعية وفق العقد المرجعي. لا تُولّد مهارات بديلة تلقائيًا أثناء استيراد البنك؛ افحص أي توسيع أحدث على Legacy أولًا.
- **هوية السؤال البصرية:** سؤال واحد وهوية واحدة ومرجع صورة/ترتيب اختيار/إجابة صحيح، مع المصدر والصفحة ورقم الكود عند وجوده؛ لا تستنتج حرف الإجابة من موضع قص الصورة.
- **أفعال المهارة:** روابط فيديو/تدريب/ملف دعم تصل إلى Topic موثوق يحمل pathId/subjectId/skillId، وتعرض قائمة المحتوى دون تشغيل فيديو أو تدريب تلقائي. لا fallback باختيار Topic ذي اسم مشابه.
- **التقارير العادلة:** لا يصنف الطالب ضعيفًا دون أدلة كافية؛ اعرض نطاق القياس وتغطيته وحداثته، ولا يقرر AI الدرجة أو الإتقان أو منح باقة.
- **ذاكرة المراجعة:** حفظ السؤال للمراجعة والخطأ لا ينشئان نسختين متنافستين لنفس الطالب والسؤال؛ يحتفظ النظام بأصل السؤال والمحاولة.
- **سياسة التدريب اللفظي VERBAL26:** لا توليد بنوك تدريب/محاكيات جديدة دون موافقة مالك صريحة؛ المشروع الأصلي لديه قيد موثق بهذا الشأن.

## 10. السرعة والأداء

الهدف: نفس ALMEAA للمستخدم، مع أداء أفضل حيث تثبته القياسات. قبل أي تحسين سجل baseline لوقت التحميل وتفاعل الصفحة، p50/p95 للـAPI، عدد الطلبات، transferred bytes، أحجام الصور والـbundle، واستهلاك الذاكرة/DB في مسار ممثل. بعد التعديل قارن بنطاق وبيانات متطابقة.

لا نسمي Go أسرع تلقائيًا دون benchmark؛ القرب الجغرافي للشبكة، استعلامات PostgreSQL، Redis، طريقة جلب المحتوى، والصور تؤثر. لا preload لكل محتوى الطالب، ولا تمرير فيديو/صور كبيرة عبر JSON، ولا تمويل خدمة أو نقل منطقة بغير موافقة.

## 11. البرنامج التنفيذي المرتب من نقطة العمل الحالية

**Gate 0 — المصالحة:** فحص latest main/branches/PRs، status المحلي، الشهادات السابقة، الملفات الأصلية الحالية، وتجهيز مصفوفة GAP/UNKNOWN؛ النتيجة قائمة أولويات صغيرة قابلة للتنفيذ. لا نعيد جرد كل شيء في كل دفعة.

**Gate 1 — الموقع العام:** إنهاء PR #152 بعد CI للرأس النهائي؛ الاستكمال التالي لإعدادات الهيدر والصفحة الرئيسية الديناميكية والهوية والروابط/الدخول، مع حفظ #150/#151 وعدم إعادة بنائهما.

**Gate 2 — إدارة المسار والمادة:** الشريحة P0 المفصلة في القسم 7، لأن المالك أثبت اختلافًا أساسيًا؛ اختبار المدير→الطالب والتخزين.

**Gate 3 — الرحلة التعليمية:** الطالب/ساحة التعلم/الفيديو/التدريب/الدورة/الاختبار/النتيجة/المراجعة/التقارير/المسار الذكي، وإصلاح دلتا الأصل فقط، مع مراجعة شهادات UI-3/UI-4 السابقة دون افتراض تطابقها النهائي.

**Gate 4 — الأدوار والمؤسسات:** إدارة المنصة المتبقية، مدير المدرسة والمعلم والمشرف وولي الأمر والفصل الذكي والتكليفات والمدفوعات. كل موديول شرائح عابرة للأدوار، لا ستة محركات منفصلة.

**Gate 5 — تكامل البيانات والخدمات:** مراجعة علاقات Go/PostgreSQL، R2/Redis/AI/العمليات، المحاكاة والتقارير، ثم ترحيل بيانات تجريبي فقط ببوابة استعادة ومصالحة.

**Gate 6 — اعتماد ما قبل الإطلاق:** E2E all-role + paired visual + RBAC/tenant denial + restore drill + performance + releases/observability/rollback، ثم قرار مستقل NOT READY أو CONTROLLED PILOT READY أو PRODUCTION READY حسب الأدلة. لا يُغيّر الإنتاج في هذا التكليف.

**ترتيب تنفيذ مرن:** يعتمد على الدومين والسلوك ونقاط الخطر، لكن لا يتجاهل العطل الذي أبلغ عنه المالك ولا يفتح عشرة فروع تتصادم. كل Gate ينتهي بتسليم فعلي واختبار مستقل، وليس ورقة جديدة.

## 12. تعريف Done لكل شريحة

لا يُسمح بوسم DONE/PARITY_PROVEN إلا بتسجيل:

- أحدث legacy SHA/target SHA والملفات/شاشة/دور/أفعال مقارنة.
- مصدر العقد البصري وسير العمل وروابط التنقل.
- اختبار فشل واضح قبل الإصلاح، ثم نجاحه بعده.
- E2E حقيقي مع Go/PostgreSQL أو تمييز سبب عدم إمكانه؛ تسجيل حد كل mock.
- حالات نجاح، خطأ، إلغاء، فقد صلاحية، بقاء البيانات، رجوع/Reload، وحالة بيانات فارغة.
- Screenshots paired بنطاق وحالة مماثلين على المقاسات المعنية، وغياب RTL overflow.
- اختبار صلاحيات server-side ولو كان الزر غير ظاهر في React.
- أثر على الإتاحة والتجارة والقياس والتقارير والتعلم، أو إثبات عدم التأثير.
- الاختبارات الأربع المطلوبة في مشروع Go على **SHA النهائي**، ومراجعة PR، ورابط evidence وحالة غير المثبت.
- تحديث مختصر داخل docs/migration/03 و26 وCURRENT_STATE فقط حسب ما تغير؛ لا master جديد ولا 100% وهمية.

## 13. أشياء ممنوعة

- إعادة بناء Go أو PostgreSQL بالكامل بلا تقرير تكلفة/خطر يقارن الإصلاح بإعادة البناء.
- نسخ صفحات legacy مع business logic/Store/Mongo dependencies بالجملة.
- استخدام جدول CRUD جديد بدل مساحات عمل أصيلة.
- اعتبار 55 route مقابل 54 أو 306 ملفات مقابل 64 نسبة تكافؤ.
- زخرفة شاشة بعناصر أو أرقام وهمية أو اختبارات تنجح بالمحاكاة فقط.
- تعطيل صلاحية أو قيود أو مراجعة أو CI لتمرير التنفيذ.
- تعديل Legacy أو بيانات الإنتاج أو تغيير الاستضافة/الدومين أو تنفيذ cutover.
- مزج فروع Gemini/Work أو دمج PRs قديمة wholesale، أو تشغيل كاتبين على الفرع نفسه.
- إعادة فتح وظيفة verified دون خلل مثبت، أو إعلان إنتاج جاهز من green CI وحده.

## 14. توزيع الأدوار والتواصل

**ChatGPT Work — منفذ أساسي:** يقرأ خطة Go الحالية، يستكمل PR الجاري، ويطبق شرائح RED→GREEN، ويرفع PRs ويثبت CI مع تغيير دقيق. يملك قرار كيفية صياغة Go والـSQL ما دام العقد الخارجي ثابتًا.

**المالك ناصف — قرار المنتج فقط:** يُستدعى عند تعارض حقيقي في سلوك معتمد، أو تغيير في السياسة التعليمية، أو كلفة/بيانات/إطلاق/صلاحيات لا تغطيها الاتفاقات الحالية؛ لا يُطلب منه تحديد شكل وحدات Go أو SQL.

**تقرير كل دورة:** baseline SHA؛ ما اتغير؛ ماذا جُرّب فعلًا؛ PASS/PARTIAL/UNKNOWN/BLOCKED؛ اختبارات CI وروابط الأدلة؛ الفرق الباقي؛ القرار التالي. رد بسيط للمالك وليس سرد أدوات.

## 15. أمر تشغيل مختصر لإرساله إلى Work

> اعتمد هذه الوثيقة كتقرير مراجعة مستقل تابع للخطة الحالية docs/migration/03_EXECUTION_AND_HANDOFF_PLAN_AR.md، لا تنشئ Master Plan جديدة. استمر من فرعك وPR الجاري بعد تثبيت أحدث SHA والتغييرات المحلية، ولا تعد تنفيذ ما ثبت سابقًا. أسلوب العمل المعتمد هو Modular Monolith في Go/PostgreSQL، لكن وحدة التسليم هي Vertical Capability Slice عبر كل الأدوار التي تستعملها، مع إعادة واجهات وتبويبات وسير عمل ALMEAA الأصلية حرفيًا من حيث تجربة المستخدم. ابدأ بإكمال الموقع العام الجاري، ثم رحلة المدير بطاقات المسارات→مساحة المسار→بطاقات المادة→مساحة المادة→النشر→ظهور الطالب، مع إصلاح الفجوات المثبتة وتقريرها. بعد ذلك اعبر موديولًا موديولًا عبر كل اللوحات والأزرار والروابط، وأثبت كل actor→screen/action→HTTP→Go→PostgreSQL→UI، مع اختبار حالات النجاح/الرفض/الإعادة/الحفظ/RTL وصور Legacy/Go المقترنة. لا تغيير للدرجة/الخصوصية/الدفع ولا cutover، ولا ادعاء Parity دون دليل حي. أعطني كل دفعة PR صغيرًا مكتمل الاختبارات على SHA النهائي وجدول GAP/UNKNOWN واضحًا.
