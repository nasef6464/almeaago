# البرومبت الموحد الجاهز لإرساله إلى Gemini

أنا مالك ALMEAA. أكلّفك باستلام وتنفيذ مطابقة المنصة كاملة، بنفس واجهات وتجربة ووظائف وعلاقات وصلاحيات المشروع القديم، على Go/PostgreSQL في الجديد، مع المحافظة على المنجز الصحيح وتنظيم الموديولات. الصور والأعطال التي أرسلتها أمثلة؛ لا تحصر النطاق فيها.

أنت المدير الهندسي المساعد والمنفذ، وCodex المشرف الذي يراجع التسليمات والأدلة عند إرسالها إليه. لديك تفويض للعمل بفريق وكلاء متخصصين، وتشغيل الأدوات والاختبارات والمتصفحات والبيئات المحلية المعزولة وتثبيت ما تحتاجه محليًا بصورة مبررة، ضمن تعليمات المستودع وحدود حماية المصدر وبيانات الإنتاج.

المرجع القديم المحلي: `C:\ALMEAA MAY - codax`، ومستودعه `https://github.com/nasef6464/almeaacodax.git`.
الجديد: `https://github.com/nasef6464/almeaago.git`، وجذر Git المتوقع `C:\almeaago\almeaago`؛ تحقق من الجذور الفعلية قبل العمل.

ابدأ بقراءة الملف التالي كاملًا:

`C:\almeaago\almeaago\docs\migration\GEMINI_WHOLE_PLATFORM_DELIVERY_CONTRACT_AR.md`

هذا هو عقد العمل التفصيلي: يشمل المراجع والخريطة الشاملة وفلسفة التعلم والمدارس والتجارة وبقية المجالات، وتنظيم الفريق وتسليم الوكلاء، ومقارنة UI/API/Go/التخزين، والاختبارات والصور والأدلة وبوابات القبول والصلاحيات. طبّقه مع AGENTS والخطة الرئيسية والملفات التي يربطها، ولا تنشئ خطة منافسة.

إجراءاتك بالترتيب:

1. استلم المهام الجارية واحفظ أعمالها ونتائجها قبل تغيير الاتجاه. افحص Git والعمليات والوكلاء والبيئات وSHAs وأي تعديلات متزامنة.
2. اقرأ العقد والمراجع، وقارن القديم المحلي بمرجعه البعيد دون تعديل القديم أو فقد أعمال محلية.
3. حدّث الخرائط الموجودة للقدرات والشاشات والموديولات والعلاقات والصلاحيات لكل المنصة. صنّف المجهول كـUNKNOWN، وحدد المنفذ المثبت والمنفذ غير المثبت والفجوات؛ لا تبدأ بجرد فارغ جديد إن وجد مقابل صالح.
4. أنشئ فريقًا مناسبًا: فاحص للقديم، وفاحص للجديد، ومراجع تكامل، ومنفذون متخصصون، ومراجع قبول مستقل. يمكن توزيع الأدوار بالتتابع عند ضيق السعة. كاتب واحد لكل ملف، وعقد مهمة واضح لكل وكيل، وأدلة تسليم متبادلة قبل الدمج.
5. نفذ دفعات وظيفية كاملة حسب الخطة والتبعيات: حساب ودور → لوحة وإجراء → طلب → خدمة Go → تخزين/مزود → نتيجة → أثر على بقية الأدوار. قارن النسختين ببيانات اختبار مكافئة؛ أصلح الفروق ثم أعد التجربة ومراجعة الصور والصلاحيات والحفظ.
6. سلّم حالة افتتاحية موجزة ثم تقدّم بالتنفيذ؛ لا تتوقف عند تقرير أو وعد. سلّم كل دفعة بأدلتها، وسجّل حدود التحقق والخطوة التالية. الملاحظات ذات الخطر أو التعارض ترفع للمشرف، مع استمرار العمل المستقل غير المتأثر.

ممنوع إعلان اكتمال الموقع من نجاح build أو كثرة الاختبارات أو تشغيل الوكلاء. لا تعتبر PENDING نجاحًا، ولا تعالج Forbidden بفتح الصلاحيات، ولا تغيّر التصميم بحجة تحسينه، ولا تخلط موضوع التأسيس بالمهارة أو درس الفيديو. المادة العلمية ليست نطاق تأليفك أو استيرادك في هذا التكليف؛ نسّق مع المسؤول عنها وأصلح البنية والعرض والربط.

لا كتابة في القديم أو بيانات الإنتاج، ولا نشر أو cutover أو تجاوز حماية main. بيانات وتجارب الكتابة داخل بيئة اختبار معزولة. اتبع الفروع وPRs وCI المعتمدة، واحفظ الجلسات والأسرار خارج Git والأدلة المنشورة.

اجعل ملف التسليم الواحد `docs/migration/GEMINI_CURRENT_HANDOFF_AR.md`، واربط منه الخريطة والسجلات والأدلة. أول رد مطلوب بعد الفحص الأولي: baselines وحالة الجاري، الملفات التي قرأتها، التغطية الأولية للمنصة، توزيع الأدوار الفعلي، وأول دفعة بمعيار قبول قابل للاختبار. لا تكتفِ بعبارة «تم الاستلام وسأبدأ»؛ قدّم مخرجات فعلية وتابع ضمن النطاق المعتمد.
