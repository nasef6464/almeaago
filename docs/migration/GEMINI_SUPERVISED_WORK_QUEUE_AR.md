## إجراء كل دفعة

1. شغّل نفس الرحلة في الأصل والجديد بنفس الدور والحالة وبيانات اختبار مناظرة؛ صور 390 و820 و1440، مع حفظ رابط الشاشة وحالتها وSHA. اختلاف البيانات يوثق ولا يُخفى بتغيير المرجع.
2. اقرأ مكونات الواجهة الأصلية وCSS وحالات التحميل والفراغ والخطأ والأزرار والحوارات والروابط. سجل قياسات عرض الحاوية والهوامش والخطوط؛ الفراغ ليس خطأ تلقائيًا إن كان موجودًا في الأصل.
3. تتبع كل إجراء: المستخدم → عنصر الواجهة → URL/HTTP → خدمة Go → جدول/علاقة → النتيجة الظاهرة. قارنه بسلوك المصدر وتأكد من عزل الطالب/المادة/المسار والاستحقاق.
4. قدم قائمة الفروق والملفات والتغيير المقترح قبل تنفيذ دفعة واسعة. انسخ طبقة العرض الأصلية أو كيّفها فوق عملاء Go الحاليين. لا تجعل API مجرد بيانات وهمية لملء الشاشة.
5. أصلح دفعة وظيفية واحدة، واختبر الحفظ وإعادة التحميل والرجوع وتجدد الجلسة وفشل الشبكة؛ افحص الصور المقترنة ثم أصلح الفروق. اختبارات mock لا تثبت PostgreSQL.
6. سلم commit محددًا ودليل الفحص وأسماء الاختبارات ونتائجها وحدودها؛ افحص CI على الرأس نفسه قبل اعتماد الدمج. لا نشر تلقائي ولا تعديل المصدر أو بيانات الإنتاج.

## صيغة تقرير Gemini المطلوبة

- معرف الدفعة، الفرع وSHA المصدر والهدف والملفات المعدلة.
- السابق/الجديد لكل فرق؛ مراجع ملفات المصدر وأزراره وحالاته.
- الصور: original / new / diff بنفس الحجم والحالة؛ ملفات trace لفشل الرحلة.
- الطلبات والخدمات والجداول والعلاقات المتأثرة ودليل الحفظ/القراءة.
- أوامر الفحوص وexit code وCI، مع التمييز بين mock وHTTP/PostgreSQL والمتصفح الحقيقي.
- المتبقي وموانع القبول. الحالات: VERIFIED / PARTIAL / UNKNOWN / BLOCKED، بلا نسبة 100% عامة.
