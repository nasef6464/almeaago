# قبول المطابقة ومنع تكرار العيوب

مكمل لحزمة Gemini بتاريخ 2026-11-03. هدف المالك نسخ هيئة الموقع وسلوكه وتفاصيله وعلاقاته وقدراته فوق Go/PostgreSQL. تطبق هذه الآلية على جميع قدرات الجرد الشامل؛ لا تعيد تعريف الخطة الرئيسية ولا تثبت بذاتها أي إنجاز.

## 1. صورة مرجعية ثابتة لكل دفعة

قبل التعديل سجل source SHA وtarget base SHA والروابط والأدوار وحالة التسجيل/الاشتراك وبيانات الاختبار وviewport/DPR والثيم والخطوط والوقت المؤثر على البيانات. احتفظ بلقطات الأصل قبل تعديل الجديد. إذا تحرك الأصل إلى نسخة أحدث، سجل الفرق وحدّث المرجع بقرار موثق؛ لا تغير مرجع المقارنة أثناء الإصلاح لتجعل الاختبار ينجح.

لا تستخدم جلسة المالك أو بياناته الشخصية في حزمة قابلة للنشر. أي بيانات مناظرة تُجهز في بيئة اختبار معزولة؛ إن تعذرت المناظرة سجل محدودية المقارنة بدل شهادة شكلية كاذبة.

## 2. سجل قبول ذري

ملف `acceptance-ledger.csv` ضمن أدلة الدفعة، صف لكل فعل/حالة لا لكل صفحة فقط. الأعمدة:

```csv
id,capability,role,scope,entry,action,expected_legacy,legacy_code,target_code,api_contract,data_owner,preconditions,expected_effect,viewport,visual_evidence,functional_evidence,regression_evidence,target_sha,status,reviewer,next_action
```

الأدلة قد تكون روابط artifacts أو ملفات محلية موثقة. أنشئ صفوفًا منفصلة لفتح القائمة، فتح نافذة، حفظ، رفض، retry، reload، back، والتأخر عند تبديل السياق حسب السلوك الموجود. لا تضع عدة حالات وراء حكم PASS واحد. ادعاء «نفس القديم» يتطلب مرجعًا وفحصًا لكل التفاصيل ذات الصلة.

الحالات: UNKNOWN، DISCOVERED، IMPLEMENTED، FUNCTIONALLY_VERIFIED، VISUALLY_VERIFIED، ACCEPTED، BLOCKED. لا يلزم تمثيلها خطيًا إذا تحقق الشكل قبل الوظيفة؛ احفظ الدليلين مستقلين، وACCEPTED لا يأتي إلا بعدهما مع الصلاحيات والانحدار والمراجعة. BLOCKED يحتاج السبب وما الذي يفك التعطل، لا يستخدم لإخفاء عمل غير مكتمل. النسبة المبنية على عدد الصفوف تنظيمية فقط ولا تعني نسبة مطابقة المنتج.

## 3. كتالوج سيناريوهات قابل لإعادة التشغيل

لكل رحلة اكتب خطوات قصيرة ومدخلات محددة ونتيجة متوقعة، ثم آلي ما يستحق الأتمتة. احتفظ بسيناريوهات حساب جديد، حساب ببيانات، فارغ، فشل طلب، غير مستحق، ودور/مسار/مادة أخرى حيث تنطبق. لا تعمم هذه الحالات على قدرة لا تستخدمها.

الحالات المرجعية المهمة تشمل: طالب مسجل وغير مسجل؛ عدة مسارات؛ موضوع فرعي بصفر/درس/عدة دروس؛ السؤال نفسه في نشاطين بإصدار مثبت؛ صورة تحتوي الخيارات مقابل نص الخيارات؛ محاولة درجة صفر أو جميعها صحيحة أو متروكة؛ محاكي مادتين؛ تقرير مخفي؛ مهارة بلا ربط تأسيس؛ إعادة تسليم؛ مستخدم من مدرسة/فصل آخر؛ باقة فعالة ومنتهية. هذه بيانات صناعية، وليست تكليف إدخال مادة علمية.

لا تعدل seed ثابتًا لتجاوز إخفاق الاختبار. كل سيناريو يذكر ما يجهزه وما يحذفه في بيئته المعزولة. بيانات الإنتاج ليست fixture.

## 4. المقارنة المزدوجة

قدرة واحدة في الأصل والجديد، ثم حكمان مستقلان:

- مطابقة العرض والتفاعل: القياسات والصور وحالات العناصر والتنقل والحوارات والنصوص والصوت/الفيديو إن وجدت.
- مطابقة الدلالة والأثر: ما حدث في الخادم والتخزين والصلاحية والرسائل والأثر على المستهلك التالي.

تختلف UUIDs والتخزين وصياغة HTTP بين النظامين؛ لا تطلب تطابق JSON حرفيًا إن كانت الدلالة محفوظة. أنشئ خريطة هوية صريحة للسيناريو. التوقيت والطلبات المتأخرة وحالات الفشل جزء من السلوك. لا تعتمد صورًا وحدها ولا API ناجحًا وحده.

## 5. حماية بقية المنصة

لكل تغيير سجل المستهلكين والعقود المتأثرة من بحث الكود، ثم حدد اختبارات الانحدار الضرورية. التغيير في shell أو auth أو taxonomy أو مشغل مشترك أو إعدادات أو DTO مشترك يحتاج فحص مستهلكيه، لا الصفحة التي حفزت الإصلاح فقط. حدّد مجموعة رحلات دخان قصيرة للمشروع من الجرد؛ لا تخترع قائمة تزعم شمول كل المنصة قبل الجرد.

احفظ الفرق بين فشل سابق وفشل أحدث بسبب الدفعة. لا تتجاهل فشلًا مجهول السبب. لا تستبدل نتائج CI على رأس قديم بالنتائج على رأس التسليم. عند تغيير الكود بعد الفحوص، أعد الفحوص التي يتأثر بها التغيير وسجل SHA النهائي.

## 6. مراجعة مستقلة وإغلاق

Gemini يسلم الأدلة ونتيجة اختباره، ثم Codex يعيد خطوات ذات مخاطرة من السجل ويقرأ التغيير ويقارن الصور. الوكيل المراجع لا يعتمد فقط ملخص الوكيل الكاتب. إذا كانت المراجعة آلية/ساكنة فقط يذكر ذلك؛ ليست بديلًا عن التحقق الفعلي.

مخرجات المراجعة: ACCEPT للنطاق المحدد أو RETURN مع IDs عيوب قابلة لإعادة الإنتاج، دون مدح عام أو «100%» غير مسند. كل عيب له severity وtrigger وexpected/actual ومرجع ودليل وإصلاح مطلوب وفحص إعادة قبول. المسميات الحرجة: فقد وظيفة، مسار خاطئ، عدم حفظ، خلط نطاق، تجاوز صلاحية، اختلاف تصميم، اختلاف تفاعل، تراجع قدرة أخرى.

أغلق الدفعة بعد عدم بقاء مانع قبول، والفحوص المطلوبة وCI على الرأس النهائي. دمج الكود والنشر وترحيل البيانات مراحل مستقلة وفق صلاحيات المشروع؛ لا تحول قبول دفعة إلى إذن تلقائي بالإنتاج.

## 7. طلب تغيير ومنع إعادة التصميم الصامت

أي اختلاف متعمد عن الأصل يسجل في `intentional-differences.md`: السلوك القديم، المقترح، السبب، الأثر، صاحب القرار وحالته. الأصل يبقى المرجع ما لم يعتمد المالك تغييرًا. تثبت حدود مزود خارجي مثل يوتيوب ويبلّغ أثرها بدل الوعد بإخفائها أو تجاوزها.

لا تستعمل «تنظيم المودولات» لتغيير رحلة الطالب، ولا «تحسين الأداء» لحذف تبويب أو حصر القائمة لأول صفحة. افصل الإصلاح الداخلي عن التغيير المرئي المقترح.

## 8. نموذج بطاقة دفعة ترسل إلى Gemini

```text
Batch ID:
قدرة المستخدم وحدود الدفعة:
Source SHA / target base SHA / branch:
مرجع الأصل: ملفات + روابط + صور الحالات:
لماذا توجد القدرة وما الذي يحدث بعدها:
صفوف acceptance-ledger المطلوب إغلاقها:
قواعد النطاق والإتاحة والدرجات/التقدم ذات الصلة:
API وخدمة/جدول المالك والعقود المتأثرة:
الملفات المحجوزة ومالك كل ملف:
المستهلكون واختبارات الانحدار:
بيئة الاختبار والبيانات الصناعية:
الفحوص والصور المطلوبة:
الاختلافات المقترحة التي تحتاج قرارًا:
تسليم commit/PR/CI/artifacts والمتبقي:
```

يملأ المشرف البطاقة من الجرد المكتشف؛ لا يترك «كل شيء» تكليف تنفيذ مفتوحًا لوكيل واحد. شمول المشروع يتحقق بتغطية سجل القدرات كله عبر دفعات محددة قابلة للمراجعة.
